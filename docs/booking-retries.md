# Durable booking operations

`src/server/booking-operation.ts` is a backend-only boundary, not an HTTP API. Recovery credentials use persistent browser storage; same-origin JavaScript can read them, so an XSS compromise can steal them. Do not expose submission until durable browser allocation, authenticated registration/resolution, same-origin protection and independent-tab recovery are integrated and verified. Never put contacts or notes in browser storage or log credentials, canonical payloads, fingerprints, SQL bind parameters or booking responses.

## Intent and configuration

`createBookingOperations(keys)` takes independent durable 32-byte HMAC and AES key rings, each with a current ID. Keys must come from trusted server configuration, never a request; there are no ephemeral defaults. The instance copies key buffers. Retain old IDs and their unchanged keys through all live replay obligations; losing keys must not authorize replacement bookings. No environment-variable loader or key generation-on-startup is provided.

`createIntent(db, clock)` creates an independent public UUID locator and random 32-byte hex credential for backend callers. Only its SHA-256 hash is persisted. Pending submission expires exactly 24 elapsed hours after creation. It is not a browser fallback: a server-generated credential whose response is lost is not durably held by the browser.

`registerIntent(db, { operationId, credential }, clock)` registers a pair already retained by its caller. Both fields must be primitive strings: a lowercase UUID locator and exactly 64 lowercase hexadecimal credential characters. The browser must generate a fresh locator with `crypto.randomUUID()` and an independent credential with `crypto.getRandomValues()`. Browser entropy cannot be verified by the server; never derive a credential from contact fields, the locator or time. Server code stores only its SHA-256 hash and sets the original creation time and 24-hour submission deadline using the trusted server clock.

Registration atomically inserts if absent, then locks/authenticates the row. Matching retries leave **every** existing field unchanged, including pending deadlines, committed replay material and terminal state. A locator with a different credential, or a credential reused under another locator, fails with `operation_unavailable`; neither uniqueness constraint may overwrite an existing row. Database failures and lock timeouts are `recovery_unavailable`, with no nested cause. Registration returns no receipt or lifecycle status; success does not mean the operation is eligible to submit. A lost acknowledgement must retry the same saved pair, never generate a replacement.

The browser integration must commit each pair to IndexedDB **before** registration or submission. Transaction completion, not an individual request's success, establishes storage success. Count all retained records and insert within the same readwrite transaction; refuse at **16 or more**, without silently evicting anything. Failed, blocked or aborted storage must prevent networking rather than fall back to cookies or tab memory. This limit covers app-managed records in the same origin/storage partition, not manual tampering, other profiles or storage partitions. Browser clearing or eviction can destroy recovery credentials; storage is not a backup or a guarantee against browser-managed data loss. Do not automatically remove records on expiry or an unavailable response, and never let a delayed response reinsert a record. Actual browser allocation, capacity checks and recovery UI are not implemented by this backend module.

## Resolve without resubmitting

`resolveIntent(db, credential, clock)` authenticates a copied primitive credential pair under the same bounded operation-row lock. It returns only `{ state: "pending", submitBefore }` before the original pending deadline, or `{ state: "committed", receipt }` using the existing receipt checks below. It needs no contact details or original agreement and does not consult the current catalog. It never registers missing rows, submits bookings or changes lifecycle/access data. Existing `recover` behavior is unchanged.

The trusted clock is sampled after acquiring the lock, including for terminal rows. At the exact pending deadline or confirmation expiry, resolution fails with `operation_unavailable`. Missing/wrong credentials, terminal rows and incomplete/unsupported committed metadata use that same generic code, preserving existing receipt semantics. Inconsistent authoritative expiry, missing keys, corrupt ciphertext and token-hash mismatches fail with `recovery_unavailable`; database failures/timeouts are redacted without a cause.

A pending result is **only a snapshot**: another request can submit immediately after the lock is released. No result or error permits removing a retained record, freeing capacity or automatically starting a replacement. Missing rows cannot rule out a delayed registration. Unknown outcomes retain the same pair; register an already-retained, unregistered pair idempotently before resolving it. Explicit-clear fencing remains unimplemented.

## Submit and recover

`submit(db, credential, input, clock)` and `recover(db, credential, clock)` return only `{ appointmentId, confirmationExpiresAt, viewToken }`. The token is sensitive: transport must enforce private, no-store responses and the reviewed private-link mechanism. This module does not build confirmation URLs.

Submission keeps the operation lock through booking, keyed fingerprint comparison and authenticated token recovery. Identical committed submissions return the same receipt without consulting the current catalog or default phone country; changed submitted agreements fail with `payload_conflict`. A failed transaction leaves the existing pending intent reusable until its deadline. `recover` cannot execute a pending booking.

Replay is valid only before the appointment's original service-end + 168 elapsed-hour expiry, even when the submission deadline has passed. AES-256-GCM stores a 12-byte nonce, 32-byte token ciphertext and 16-byte authentication tag; authenticated data binds version, operation, appointment and expiry. Recovered tokens must match the stored access hash. Old key IDs remain readable after rotation. Missing keys or corrupt/inconsistent replay data fail closed.

`booking_busy` and `recovery_unavailable` are **unknown**, not evidence that nothing committed. Keep the same intent and resolve/retry it; never mint a replacement automatically. Error codes contain no query values or causes. Log neither function arguments/results nor database error objects. `operation_unavailable` covers wrong credentials, noncommitted recovery and expired/terminal operations. Booking validation/conflict codes remain those of `bookAppointment`.

## Retention

`pruneExpired(db, operationId, clock)` is a trusted maintenance function, not a guest reset endpoint or scheduled job. It locks and rereads the operation. Pending intents become tombstones at their submission deadline; committed operations become tombstones only at the exact original confirmation expiry, after checking the authoritative appointment expiry. Inconsistent metadata fails without deletion. Cleanup atomically deletes access material and clears the operation's appointment association, fingerprint, ciphertext and key IDs. Appointment/contact/service/occupancy history remains intact. Terminal rows retain locator/hash/state and original lifecycle timestamps indefinitely; only an independently authorized explicit local reset may remove them. Cleanup never creates new intents. Expired replay fails even when cleanup has not run.

To roll back runtime integration, stop invoking this module; do not delete tombstones, reset data, retire live keys or fall back to the raw booking transaction. The underlying schema is unchanged. Browser storage, HTTP lifecycle resolution, explicit-clear fencing and retrieval/page privacy controls require their own reviewed transport integration; this module alone does not establish reload/tab-closure recovery in a browser. Until explicit removal is implemented, retained records can exhaust capacity. Clearing must fence pending/in-flight submission on the server before freeing a local slot; it must neither cancel a committed appointment nor silently treat an unknown outcome as permission to create another booking. Tab locators may be copied with session storage: resuming one means recovering that same intent, while explicitly starting a different intent requires a fresh record.

## Canonical agreement

Canonical agreement v1 uses ordered JSON fields: version, staff ID, ordered service IDs, UTC start instant, ordered reviewed-service snapshot values, trimmed required contact fields, verbatim note (omitted means empty), submitted phone country (omitted means null). Object property order and equivalent timestamp offsets are irrelevant; service order, phone formatting, email case and note whitespace remain meaningful. Canonicalization does not consult changing catalog or country defaults. It copies validated fields before asynchronous work. Never persist the plaintext canonical agreement.
